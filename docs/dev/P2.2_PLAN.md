### 0.1 本阶段的准确定位（一句话）

> **P2.2 = 信任边界加固 + 官方评测覆盖。**
> 不是"从零搭管线"，不是"让采集结果进报告"，也不是"做研究 Agent"。

**P2.2 做两件事，只做这两件：**

| # | 做什么 | 为什么现在必须做 |
|---|---|---|
| A | **信任边界加固**：让"官方原文"与"人工摘要"在代码层可区分；把准入条件收敛成一道可执行闸门；把"采集层不得成为证据"从隐式约定升级为类型/API 边界 | 现状两个目录的 `fixture_snapshot` **同权**，且 `source_kind` **声明了但零消费**（§5 D1）；边界只靠依赖方向间接保证，没有一条正面断言（§5 D3） |
| B | **官方评测覆盖**：给官方目录补上"固定场景 + 期望值"的回归体系，并把来源锚点核对纳入指标 | 官方链路目前**只有单元测试**，`eval/` 完全不含 `official`（§5 D4） |

**P2.2 明确不做（三个"不"）：**

1. **不实现 provider 自动升格** —— P2.1 采集到的 `provider.snapshot.v1`（GitHub 仓库搜索元数据）
   **不会**自动变成 `EvidenceRef`、**不会**进入报告。本阶段只把这条边界**做成类型/API 层的硬约束**
   并把"人工离线升格"路径**写清定义**（§2.5、§1.2），**不写实现**。
2. **不实现自主研究** —— 无查询改写、无多轮迭代、无自动结论生成；采集仍是一次性人工动作。
3. **不改既有正确管线** —— `FixtureResearchWorker`、`assemble_report`、`FixtureResearchWorker`
   的产出语义保持不变；`fixtures/**` 字节不变、签名不变、`report_id` 不变（§6.1 `G-PRESERVE`）。

这样做的直接好处：不动已经正确的管线、不碰基线、把力气花在真正缺的地方。

## 二、必须设计的契约

### 2.1 `official source` 的 `source_type` 是否新增 → **不新增**

**结论：官方原文继续复用 `source_type = "fixture_snapshot"`，不新增枚举值。**

理由（可验证，非偏好）：

1. `compute_evidence_id` 的哈希输入是
   `f"{source_type}|{source_id}|{snapshot_version}|{locator}|{digest}"`
   —— **`source_type` 参与哈希**。新增/替换 `source_type` 会改变**每一条** `evidence_id`
   → 改变 `finding_id` → 改变 `report_id`。
2. 现有 `report_id` 是**硬回归锚点**（README 表格、`test_official_report_ranking_is_pinned`、
   `eval/expectations/*.json` 共 10 个场景）。硬约束"不破坏 P1A 基线和既有 report_id"直接禁止这条路的"改类型"走法。
3. 官方目录已经用 `research.fixture.v1` schema，`OfficialSources.worker()` 复用同一 loader，
   新增类型等于把一条**已经跑通且被测试钉死**的路拆掉重铺。

**那"区分不同来源"靠什么？** 靠**不进哈希**的三层标记：

| 维度 | 载体 | 是否进 `evidence_id` 哈希 |
|---|---|---|
| 目录级来源性质 | `source_kind`（目录内每份文件声明） | 否 |
| 版本与批次 | `snapshot_version` = `<candidate>.<set>.<date>` | **是** |
| 候选归属 | `source_id` = `fixture:<candidate_id>` | **是** |
| 采集日期 | `captured_at`（来自快照元数据，非 `now()`） | 否（但进 `report_id`） |

`snapshot_version` 里的 `<set>` 段（`official` / 无）已经能把两个目录的证据分开
（`test_official_evidence_ids_do_not_collide_with_p1a` 钉死了这点）。

### 2.2 哪些条件满足后才允许进入 `TRUSTED_SOURCE_TYPES`

**结论：`TRUSTED_SOURCE_TYPES` 保持 `{fixture_snapshot}` 不扩张。**
但把"什么内容有资格被写成 `fixture_snapshot`"从"散在 4 个文件里的隐式约定"
收敛成**一道显式闸门**（本阶段只定义，P2.2-1 实现）。

### 2.2.1 闸门被切成两段：加载期可判定的 7 条 + 外部证明的 1 条

**这是本版最重要的修正。** 上一版把 C6 设计成"往 provenance 里加 `verification` 块"，
**与"`fixtures/**` 零字节变化"直接矛盾** —— 加字段就是改 fixture 字节，必然触发重签。
本版把 C6 **移出 fixture**，改为**外部证明文件**。

| # | 条件 | 判定位置 | 需要原件？ | 现状 |
|---|---|---|---|---|
| C1 | 来源 repo 在 `ALLOWED_SOURCE_REPOS[candidate_id]` 白名单内 | **加载期** | 否 | `sources.py` |
| C2 | `url` / `raw_url` commit-pinned 且与 `repo+commit_sha+path` 逐字一致 | **加载期** | 否 | `sources.py` + 静态守卫 |
| C3 | 必须有 `commit_sha` / `blob_sha` / `raw_sha256` / `raw_lines` | **加载期** | 否 | `sources.py` |
| C4 | 必须有 `provenance` 块且通过 `read_provenance` 全量校验 | **加载期** | 否 | `sources.py::read_provenance` |
| C5 | `line_range` 必须 ≤ 该文档 `raw_lines` | **加载期** | 否 | `sources.py` |
| **C6** | **摘录与原文逐字节一致** | **外部证明**（`SourceVerificationAttestation`，§2.2.3） | **是** | `tools/verify_sources.py`（工具，尚未落成工件） |
| C7 | 文件级 digest 必须与 `INDEX.json` 一致 | **加载期** | 否 | `snapshot.py::_verify_file_digest` |
| C8 | 每条证据必须能 `resolve_evidence` 回 `SourceDocument` | **加载期** | 否 | `sources.py::resolve_evidence` |

**C1–C5 / C7 / C8 全部可在加载期判定**（只读本地 JSON，不碰原件），
因此它们**不需要**外部工件，也**不会**修改 fixture 字节。

**C6 是唯一需要原件的条件**，因此它**必须**活在 fixture 之外 —— 见 §2.2.3。

### 2.2.2 两段闸门的三种组合结果

| 情形 | 加载 | `is_promotable_source` | 可否进 `research_grade` 推荐 |
|---|---|---|---|
| C1–C5/C7/C8 全通过 **且** 有 `passed` attestation | 成功 | **True** | **可以** |
| C1–C5/C7/C8 全通过 **但** 无 attestation（**没有原件，离线回放**） | **成功**（允许回放） | **False** | **不可以** |
| C1–C5/C7/C8 任一条失败 | **失败**（抛错） | — | — |

**关键语义（对应审阅意见）**：

- **没有原件时允许离线回放**：`fixtures/official` 照常加载、照常组装报告
  （既有 `official_report` 与全部既有测试**不受影响**），
  只是这个快照集**不能被声明为可升格**。
- **只有 `verify_sources` 通过并产生 attestation 之后**，该快照集的证据才允许进入
  `research_grade` 推荐。
- **缺 attestation 不是错误，是"未验证"**：加载期**不因它抛错**，
  它只让 `is_promotable_source` 为 `False`。这样"离线回放"与"研究级推荐"被彻底分开。

### 2.2.3 `SourceVerificationAttestation`：C6 的外部证明工件

**为什么它必须在 fixture 之外**：C6（摘录与原文逐字节一致）是**唯一需要原件**的条件。
若把它写成 fixture 内的字段，就等于修改 fixture 字节 → 触发重签 → 违反 §6.1.1 `G-PRESERVE`。
因此 C6 的结论必须以**独立工件**承载。

#### 存放位置

```
attestations/                       ← 新增，**项目根**下的独立目录（不在 fixtures/ 内）
  official.sources.v1.json          官方快照集的验证证明
```

**为什么放项目根而不是 `fixtures/`**：

1. `fixtures/**` 的"零字节变化"因此升级为**最强形式** —— 既不改也不增，完全冻结；
2. 不会被 `tests/test_static_guards.py::_iter_fixture_files` 扫到
   （该函数只 `rglob` `fixtures/research` 与 `fixtures/official` 两个子树），
   因此**不会**触发 `test_official_fixture_urls_are_allowlisted` 等 URL 守卫的误报；
3. 不会被 `sign_fixtures.py --check` 读取（它只读 `INDEX.json` 登记的路径），
   因此**签名校验结果不变**；
4. `verify_manifest.py` 只守卫 `scripts/` 前缀，新增目录不受影响。

**为什么放项目根而不是 `var/`**：README 明确 `var/` 是"运行时产物、可随时删"。
attestation 是**需要长期留存、可复核、应进版本控制**的证明，语义上不属于 `var/`。

#### 字段（全部确定性，**零时间字段**）

| 字段 | 类型 | 含义 | 来源 |
|---|---|---|---|
| `schema` | str | 固定 `"source.verification.attestation.v1"` | 常量 |
| `snapshot_set_id` | str | 被证明的快照集（如 `official.2026-09-23`） | 与 §P2.2-3 一致 |
| **`index_sha256`** | str(64hex) | **被证明的 `INDEX.json` 的实际字节摘要** | 读取 fixture 目录的实际字节 |
| **`snapshot_files[]`** | list | **被证明的快照文件清单（自绑定锚点，见 §2.2.4）** | 读取 fixture 目录的实际字节 |
| `snapshot_files[].path` | str | 快照文件相对路径（POSIX，如 `sources/pgvector.json`） | `INDEX.json` 登记 |
| `snapshot_files[].sha256` | str(64hex) | **该文件的实际字节摘要** | 读取该文件字节 |
| `snapshot_files[].candidate_id` | str | 该文件属于哪个候选 | `INDEX.json` 登记 |
| `verifier` | str | 执行核对的工具标识，固定 `"tools/verify_sources.py"` | 常量 |
| `verifier_version` | int | 核对**规则**版本（规则变更时手动递增） | 常量 |
| `algorithm` | str | 核对算法的确定性描述，固定 `"sha256+git_blob_sha1+line_slice"` | 常量 |
| `documents[].source_id` | str | 被核对文档 | provenance 已有 |
| `documents[].raw_sha256` | str(64hex) | 该文档**登记**的内容摘要（被证明对象） | provenance 已有 |
| `documents[].blob_sha` | str(40hex) | 该文档**登记**的 git blob（被证明对象） | provenance 已有 |
| `documents[].line_ranges` | list[str] | 已核对的行区间，**排序后** | 由 `sections[]` 派生 |
| `documents[].result` | str | 该文档结论：`passed` / `incomplete` | 核对结果 |
| `overall_result` | str | 汇总：`passed`（全部 passed）/ `incomplete`（有缺失但无不符） | 汇总 |

**`documents[]` 的顺序**：按 `source_id` 字典序。**`line_ranges` 内部**：按数值升序。
**`snapshot_files[]` 的顺序**：按 `path` 字典序。三处都排序 ⇒ 与输入字典的插入顺序无关
⇒ 逐字节可复现。

### 2.2.4 自绑定：attestation 必须锚定**文件**，不能只锚定"声明值"

**这是本版的核心加固。** 只看 `raw_sha256` / `blob_sha` 有一个致命弱点：
它们是**写在 fixture 里的声明值**，不是 fixture 本身。attestation 若只与"声明值"比对，
就只证明了"**两个文件里的两句话一致**"，没有证明"**被证明的快照就是我手上这份**"。

**三层锚点（缺一不可）**：

| 层 | 锚点 | 拦住的攻击 |
|---|---|---|
| L-a | `index_sha256` == 实际 `INDEX.json` 字节摘要 | 重新签名 `INDEX.json` 以掩盖被改的 fixture |
| L-b | `snapshot_files[].sha256` == 各快照文件实际字节摘要 | 直接替换 / 编辑任何快照文件（改摘录、改行号、改 provenance） |
| L-c | `documents[].raw_sha256` / `blob_sha` == provenance 声明值 | 声称"核对的是另一份上游原件" |

**运行时校验（`is_promotable_source` 必做）**：

```
1) 读 fixture 目录实际的 INDEX.json 字节 → sha256 必须 == attestation.index_sha256
2) 读每个 snapshot_files[].path 的实际字节 → sha256 必须 == 登记者；
   且文件集合必须与 INDEX.json 登记的候选快照集合**完全一致**（不多不少）
3) 逐文档比对 documents[].raw_sha256 / blob_sha == provenance 声明值
```

**第 1、2 步是"文件级"校验**：任何一次字节改动都会让 attestation 失效，
**且不依赖 `INDEX.json` 自身的正确性** —— `INDEX.json` 被重签也没用，
因为它的摘要本身也在被证明之列。

**与 C7 的分工必须写清（否则容易误以为重复）**：

| 检查 | 判据 | 是否信任 `INDEX.json` | 目的 |
|---|---|---|---|
| C7（加载期） | 文件 sha256 == `INDEX.json` 登记的 `fixture_sha256` | **信任** | 保证"整份文件就是登记的那一份" |
| C6 自绑定（升格期） | 文件 sha256 == **attestation** 登记的 `sha256`，且 `INDEX.json` 摘要 == `index_sha256` | **不信任** | 保证"我这次要升格的，正是当初核对过的那一份" |

**结论（必须写进实现的文档字符串）**：
**attestation 不能只靠 `raw_sha256` / `blob_sha` 判断有效** —— 那只是"声明与声明一致"。
必须同时校验 `index_sha256` 与 `snapshot_files[].sha256` 这两个**文件级**锚点，
attestation 才真正绑定到当前磁盘上的这份 fixture。

#### 生成方式与写入策略

```bash
# 新增 opt-in 参数；默认行为（只核对、不写）完全不变
python tools/verify_sources.py --raw-dir <原件目录> --write-attestation attestations/official.sources.v1.json
```

- **生成是显式人工动作**，且**需要原件**；不进入默认测试门禁。
- 生成逻辑复用**既有核对流程**（`index_raw_dir` / `check_document`），不新写一套判定。
- 既有的 `--raw-dir` / `--allow-missing` / `--json` 参数与退出码语义**保持不变**。

**写入策略（四条硬规则，对应审阅意见 2）**：

| # | 规则 | 行为 |
|---|---|---|
| W1 | **默认禁止覆盖已有文件** | 目标已存在 → **不覆盖**。默认即无 `--force` 可用 |
| W2 | **已有文件内容不一致 → 失败** | 先读已有文件：内容**逐字节相同** ⇒ **幂等成功**（退出码 0，不写盘）；**不同** ⇒ 报错并退出 1，**明确拒绝** |
| W3 | **原子写入** | 写临时文件 + `os.fsync` + **`os.link` 原子排他发布**（临时文件与目标同目录；`os.link` 在目标已存在时以 `FileExistsError` 失败 ⇒ **排他由发布动作本身判定**，不存在"检查↔替换"窗口）；**不支持硬链接时 fail-closed**（拒绝写入、退出码 1，**不得**降级为非原子写入）；异常路径清理临时文件 |
| W4 | **不允许把 `incomplete` 改写成 `passed`** | 见下 |

> **W3 的两条修正是实测逼出来的，不是设计偏好**：
>
> 1. **`os.replace` → `os.link`**：`os.replace` 是**无条件覆盖**语义，"先检查目标不存在、再 replace"
>    在两者之间留了一个**真实**窗口（窗口内出现的文件被静默覆盖），与"禁止覆盖"**不等价**（已复现）。
>    `os.link` 让"谁先到"由发布动作判定，窗口消失。
> 2. **删掉"退化到 `O_EXCL` 直写"这条路**：它曾**返回成功**，于是"原子写入"这条硬约束
>    被实现自行降级成更弱的保证。`O_CREAT | O_EXCL` 只有**排他性**、**没有中断原子性** ——
>    进程在写完 `fsync` 之前被强杀会留下半写文件，而它看起来像一份"已生成的工件"，
>    无法与"被篡改"区分。**原子性无法提供时，唯一诚实的动作是拒绝**：
>    清理临时文件、明确报错、退出码非 0，把"该文件系统不支持原子排他发布"暴露给人。

**W4 的机制性保证（这是最关键的一条）**：

attestation 内容**完全由** `(fixture 目录字节, 原件集合, verifier_version, algorithm)` 决定
（§2.2.4 的排序规则 + 零时间字段）。因此：

1. **`passed` 不能被"写出来"，只能被"核对出来"** ——
   若原件不全，工具**在逻辑上无法生成** `passed` 的内容（缺文档 ⇒ 至少一个 `incomplete`）；
2. **`incomplete` → `passed` 必经一次内容变化**，而 W2 让"内容不同 ⇒ 失败"；
   因此**同一路径下无法静默改写**；
3. 要合法升级，必须先**显式删除旧文件**（这是一个**可见的、进 git 历史的**动作），
   再重新生成。方案**不声称**能阻止这一步 —— 它只保证**不存在静默改写路径**，
   且改写必然留下 diff。

**为什么用原子写入而不是直接 `write_text`**：attestation 是"证明"，半写状态的文件
（磁盘满 / 进程中断）会留下一个**无法判定**的工件。原子排他发布保证观察到的永远是
"完整旧版"或"完整新版"，不会出现中间态；**且当平台无法提供原子性时直接失败**，
而不是退回非原子写法把风险转嫁给下游。

**失败行为（写入侧）**：

| 情形 | 行为 | 退出码 |
|---|---|---|
| 目标不存在 | 原子排他创建（`os.link` 发布） | 0 |
| 目标存在且**内容相同** | 幂等成功，**不写盘** | 0 |
| 目标存在且**内容不同** | **拒绝**，报错指出差异（`snapshot_files` / `documents` 哪一项变了） | 1 |
| **平台不支持硬链接**（跨设备 / 文件系统） | **拒绝**（fail-closed），清理临时文件并说明原因 | 1 |
| 目标目录不可写 / 路径非法 | **拒绝**，明确报错 | 1 |

#### 序列化方式

- **规范 JSON**：`json.dumps(payload, ensure_ascii=False, sort_keys=True, indent=2)` + 末尾换行；
- **编码**：UTF-8，**无 BOM**，换行符 `LF`（与既有 fixture 文件一致）；
- **确定性**：同 `(fixture 快照, 原件集合, verifier_version)` ⇒ **逐字节相同**；
- 因此该文件本身可被 `sha256` 固定，任何人可重算并比对。

#### 失败行为（核对结果侧）

| 核对结果 | 是否写 attestation | 退出码 | `is_promotable_source` |
|---|---|---|---|
| 全部 `passed`（0 缺失、0 不符） | **写**，`overall_result="passed"` | 0 | **True** |
| 有缺失、**0 不符**（没有原件 → 离线回放场景） | **写**，`overall_result="incomplete"` | 0（配 `--allow-missing`） | **False** |
| **任一不符**（内容/行号/blob/sha 对不上） | **拒绝写**（不产生工件） | 1 | **False** |

（写入侧的四条规则见上文 W1–W4；两张表互不重叠：这张管"核对的结论"，那张管"能不能落盘"。）

**为什么"不符"不写工件**：`problem` 表示快照的声明与现实冲突，属于**数据完整性失败**。
为它生成一份工件会让"失败的核对"留下一个看似正式的产物。
按项目既有口径（`problem` 永不放行、`missing` 可显式放行），**不写**更安全。

**为什么"缺失"写 `incomplete`**：它诚实地记录了"核对跑过、原件不全"这一事实，
且因 `overall_result != "passed"` 而**不可能**被误当成可升格。

#### 加载与校验（`is_promotable_source` 侧）

attestation **只在需要判升格时读取**，因此**不参与** `load_official_sources` 的加载期校验
（缺它不影响加载，§2.2.2）。校验规则：

1. `schema` 必须是 `source.verification.attestation.v1`；
2. `verifier_version` 必须等于代码里的 `EXPECTED_VERIFIER_VERSION`（**过期即不可用**）；
3. `snapshot_set_id` 必须与被判定的快照集一致；
4. `overall_result` 必须是 `"passed"`；
5. **文件级自绑定（§2.2.4，L-a + L-b）**：`INDEX.json` 实际字节摘要 == `index_sha256`；
   每个 `snapshot_files[].path` 的实际字节摘要 == 登记的 `sha256`，
   且文件集合与 `INDEX.json` 登记的候选快照集合**完全一致**（不多不少）；
6. **声明级对齐（L-c）**：provenance 里的每个 `source_id` 在 `documents[]` 中恰好出现一次，
   `raw_sha256` / `blob_sha` 与 provenance 登记值**逐字相等**，且该文档 `result == "passed"`。

**注意**：不校验 `captured_at` 或任何时间字段（不存在时间字段 —— 这是设计约束的落点）。

#### 信任模型（**必须明说，不能含糊**）

**本项目不实现数字签名。** 因此必须把"attestation 凭什么可信"讲清楚，
否则会给人"这是密码学证明"的错觉。

**默认模式（离线，依赖仓库完整性）**：

- attestation 的**完整性**依赖"仓库内容不可被静默篡改"——
  即 git 历史 + 代码评审 + `G-PRESERVE` 门禁（§6.1.1）共同提供的**过程保证**；
- 它**不是**密码学保证：任何能改写仓库文件的人也能改写 attestation，
  且这种改写**无法被工具单方识破**；
- **方案明确声明这一点**，并在 `attestations/README` 与实现文档字符串里写明：
  **attestation 证明的是"有人在某个时点按登记的规则核对过这批字节"，
  不是"这批字节绝对可信"**。

**可选加强模式（不依赖 attestation 可信度）**：

| 模式 | 触发 | 行为 | 代价 |
|---|---|---|---|
| `attestation`（默认） | 提供 `attestations/*.json` | 校验 §2.2.4 的 L-a/L-b/L-c | 离线可跑 |
| **`live_reverify`（加强）** | 显式要求（如 `research_grade(require_live_verification=True)`） | **当场提供原件并重新核对**，不采信 attestation 的结论 | **需要原件目录**；仍不联网（原件由人工事先下载） |

**`live_reverify` 的意义**：它把"信任"从"仓库内容"转移到"**当场算出的字节**"——
即使 attestation 被篡改也没用，因为结论是现算的。
**代价必须写清**：它要求原件在场，因此**不能**用于"只有 fixture、没有原件"的纯离线回放。

**两模式的关系**：默认模式适用于**常规 CI 与离线回放**；
`live_reverify` 适用于"要拿这份报告的结论去做真实决策"的场合。
两者都用同一套核对逻辑（`index_raw_dir` / `check_document`），只是**证据来源不同**。

### 2.3 六个标识的生成规则（固化，P2.2 不改）

| 标识 | 规则 | 定义位置 |
|---|---|---|
| `source_id` | `f"fixture:{candidate_id}"` | `fixtures.py::_evidence_for` |
| `snapshot_version` | `f"{candidate_id}.official.{captured_at}"`（人工摘要目录无 `.official`） | 快照文件 + `INDEX.json` 交叉校验 |
| `locator` | `f"/sections/{index}/text"`（**仅此一种**形态） | `snapshot.py::section_locator` |
| `captured_at` | 快照元数据里的日期（**禁止 `now()`**，有静态守卫） | 快照文件 |
| `digest` | `sha256(excerpt.encode("utf-8"))`，**零规范化**（不 strip） | `evidence.py::compute_digest` |
| `evidence_id` | `"ev_" + sha256(f"{source_type}\|{source_id}\|{snapshot_version}\|{locator}\|{digest}")[:16]` | `evidence.py::compute_evidence_id` |

**为什么 `digest` 必须零规范化**：若对 excerpt 做 `strip()`，
"仅空白不同"的两份内容会撞成同一个 digest，从而绕过"内容变了 id 就该变"这条不变量。

### 2.4 如何保证 `locator` 能解析回原文 → **收敛成一条规则（修 D2）**

现状有**两条实现，规则不一致**（已实测复现，见 §5 D2）：

| 路径 | 实现 | 规则 |
|---|---|---|
| 组装期 `assemble._verify_fixture_locators` | `text.startswith(ref.excerpt)` | **接受任意前缀** |
| 来源层 `OfficialSources.resolve_evidence` | `expected_excerpt != ref.excerpt` 即报错 | **要求精确相等** |

**P2.2-2 动作**：抽出**唯一**的 `expected_excerpt_for(section_text) -> str`
（规则：`text` 若 ≤ `MAX_EXCERPT_CHARS` 则取全文，否则取前 400 字符），
两条路径都调它并做**精确比较**。

**兼容性论证（为什么这不会动 `report_id`）**：
现有 `_evidence_for` 产出的 excerpt 恰好就是 `text[:400]`，
与 `resolve_evidence` 期望一致 → 统一为"精确相等"后，现有全部 finding **仍然通过**。
因此这是一次**收紧但不改变既有输出**的修复。P2.2-2 必须用 §六 的双锚点断言证明这一点。

### 2.5 如何防止把"仓库搜索摘要 / 未验证网页 / 模型生成内容"当成证据

**现有防线（保留）**：

| 防线 | 机制 |
|---|---|
| 主机白名单 | `ALLOWED_SOURCE_HOSTS = {github.com, raw.githubusercontent.com}` |
| 仓库白名单 | `ALLOWED_SOURCE_REPOS`（**逐候选**声明，未登记即报错，而不是放宽校验） |
| commit 钉死 | `url` / `raw_url` 必须与 `repo+commit_sha+path` 逐字一致 |
| 静态守卫 | `find_unpinned_source_urls`（分支名当定位符即失败） |
| 类型闭集 | `ALLOWED_SOURCE_TYPES` 闭集；新类型必须改 `evidence.py` |
| 分散性守卫 | `SOURCE_TYPE_DISPERSION_GUARDS` + `test_no_scattered_evidence_construction_in_src`（`synthetic`/`legacy` 只能在指定文件构造） |
| 依赖单向 | `test_core_and_research_do_not_import_providers`（`research` 不可能 import `providers`） |

**P2.2 要补的：把边界从"字段形状检查"升级为"受控公开 API + 静态守卫"**

现状保护全是**间接**的（靠依赖方向、靠类型闭集），**没有一条正面机制**阻止
"把 `provider.snapshot.v1` 的内容拼成 `EvidenceRef`"。字段检查（"断言 provider 快照不含
`locator`/`excerpt`"）**不够**：字段是实现细节，加一个字段就绕过去了，
而且它管不住"从别处拿值填进去"。

**改为四层边界：**

| 层 | 边界 | 机制 |
|---|---|---|
| **L1 依赖** | `research/**` 与 `core` **不得** import `providers/**` | 已有 `test_core_and_research_do_not_import_providers`（保留） |
| **L2 受控 API** | 证据只能由 `PromotableExcerpt`（**唯一**合法入参类型）经**唯一公开工厂**产出 | 新增 `PromotableExcerpt` 冻结数据类；`EvidenceRef` 由 `evidence_from_excerpt()` 构造 |
| **L3 构造点** | `EvidenceRef(...)` 字面构造**只允许**出现在指定文件 | 把既有 `test_no_scattered_evidence_construction_in_src` 的覆盖范围**从 `synthetic`/`legacy` 扩展到全部 `EvidenceRef` 构造** |
| **L4 反向守卫** | `src/agentboard/providers/**` **不得出现** `EvidenceRef` / `compute_evidence_id` / `agentboard.evidence` 任何引用 | 新增静态守卫（与网络守卫同构：纯函数 + 正负控制） |

**准确的说法（不要过度声称）**：

本项目的能力边界是 **"受控公开 API + 静态守卫下不可合法生成"**，
**不是**"类型上不可表达"。理由必须写清楚：

- Python **没有**真正的构造可及性控制 —— 直接 `EvidenceRef(...)`、`object.__new__`、
  或 `import` 私有模块都是物理上可能做到的；
- 因此本方案**不声称**"不可能"。它声称的是：**在受控公开 API 与静态守卫的组合下，
  没有合法的代码路径**能从 `provider.snapshot.v1` 产出 `EvidenceRef`：
  1. `promote()` 工厂的入参类型是 `PromotableExcerpt`，**不接受任意 dict / provider 记录**；
  2. `PromotableExcerpt` **只能**由 `snapshot.py` / `sources.py` 从**已通过 C1–C5/C7/C8 的
     `FixtureSnapshot`** 构造 —— 拿到该类型即**蕴含**已通过来源校验；
  3. L3 守卫保证 `EvidenceRef(...)` 字面构造不出现在指定文件之外；
  4. L4 守卫保证 `providers/**` 连 `agentboard.evidence` 都引用不到；
  5. `providers/**` 里**不存在**任何适配器能把采集记录变成 `PromotableExcerpt`。

- **这是可验证的工程边界，不是形式化保证。** 绕过它需要对代码做**蓄意修改**
  （改类型注解、删守卫、monkeypatch），而那些修改会被 L3/L4 守卫与代码审查捕获。
  方案不把"物理不可能"当卖点，避免给出无法兑现的保证。

**负面测试（必须证明边界可证伪，不是纸面约定）：**

1. **构造不可达**：断言 `PromotableExcerpt` 的唯一构造入口要求 `FixtureSnapshot` +
   `SectionSource`，传入任意 dict / provider 记录类型 → `TypeError`/`ValueError`；
2. **伪造必失败**：手工拼一份**字段齐全**（含 `locator` / `excerpt` / `digest` 全对）的
   provider 风格 payload，断言它**仍然**无法经合法工厂变成 `EvidenceRef`
   —— 因为它不是受控 API 接受的类型；
3. **反向守卫可证伪**：在 `providers/` 里临时插入一行 `from agentboard.evidence import EvidenceRef`，
   断言静态守卫**变红**；移除后恢复绿（反空转对照实验）；
4. **构造点守卫可证伪**：在 `research/` 的任意非指定文件里插入一次 `EvidenceRef(...)` 构造，
   断言 L3 守卫变红。

**`source_kind` 强制**（修 D1）：让"官方原文"与"人工摘要"在**加载期**可区分 —— 见 §2.6、§2.7。

| **网络检索元数据** | `provider.snapshot.v1` | **不是 EvidenceRef**，谈不上信任级 | **否**（受控 API 下无合法路径） | `var/snapshots/` | 不可以（本阶段显式禁止） |

### 2.6.1 两个信任谓词的分工（这是本阶段最关键的一条设计）

**问题**：`is_trusted_evidence(ref)` 只判 `ref.source_type in TRUSTED_SOURCE_TYPES`。
两个目录都产出 `fixture_snapshot`，因此**同权**（§5 D1）。
但如果直接收紧 `TRUSTED_SOURCE_TYPES` 把人工摘要排除出去，会立刻**改变 P1A `report_id`**：

- `assemble.build_recommendations` 用 `is_trusted_evidence` 过滤 `supporting`；
- `models.derive_coverage` 用 `derive_coverage` 算 `trusted_finding_ids`；
- 这两者都在 `SelectionReport.content_projection()` 里 ⇒ 进 `report_id`。

⇒ 硬约束"不改 P1A report_id"**禁止**就地修改 `is_trusted_evidence` 的语义。

**解法：不复用、而是并列 —— 加一个更严的新谓词，且把它做成"按快照集生效的策略"。**

| 谓词 | 语义 | 谁在用 | 是否进 `report_id` |
|---|---|---|---|
| `is_trusted_evidence(ref)` | **既有语义冻结**：`source_type ∈ TRUSTED_SOURCE_TYPES` | 既有组装/打分/覆盖统计 | 是（**因此不得改**） |
| `is_promotable_source(source_kind, has_provenance, checks, attestation)` | **新增**：只有"官方原文 + provenance 齐备 + C1–C5/C7/C8 通过 + **有效 attestation**"为真 | 新增：来源层策略 + 新增评测指标 | 否（**不接入既有 report_id 计算**） |

配套引入**快照集策略**（`snapshot_set_policy`，挂在 §P2.2-3 的 `snapshot_set_id` 上）：

| 策略 | 用于 | 推荐支撑的准入 |
|---|---|---|
| `regression_replay` | `fixtures/research/`（P1A 基线） | 维持既有 `is_trusted_evidence`（**保证 P1A `report_id` 逐字节不变**） |
| `research_grade` | `fixtures/official/` | **额外要求**每条 `supporting` 证据的候选满足 `is_promotable_source == True` |

**为什么这样能满足"official 才可作为真实研究推荐的可信支撑"且不破坏基线**：

- 官方集里**全部**证据本来就是 `official_documentation_excerpt`，
  在有 attestation 时 `research_grade` 断言**成立**；
- **但在没有 attestation 时**（当前仓库就是这种状态 —— 尚未生成 attestation），
  `research_grade` 会判定为不可升格。因此**不能让官方路径默认走 `research_grade`**，
  否则推荐的 `supporting` 会变空、`report_id` 会变 —— 违反硬约束。
  **故 `research_grade` 是显式 opt-in**（§P2.2-3），既有调用一律保持默认 ⇒ `report_id` 不变；
- P1A 集走 `regression_replay` ⇒ **不受新策略影响** ⇒ P1A 10 个场景 `report_id` **不变**；
- 人工摘要被**明确地**降级为"仅供 P1A 回归兼容"：它能通过既有的（宽松）信任检查以复现基线，
  但**不是** promotable，因此在任何 `research_grade` 报告里都**不能**支撑推荐
  —— 这正是审阅要求的口径。

**当前 `fixtures/research/{pgvector,qdrant_local,milvus_standalone}.json` 的 `source_kind` 已是
`authored_summary`，因此该策略无需改任何 fixture 文件字节**（§6.1.1 `G-PRESERVE`）。

### 2.7 `is_promotable_source()` 的可执行规格

**签名（纯函数，零副作用、零 I/O、不读时钟）**：

```
def is_promotable_source(
    *,
    source_kind: str,                        # 闭集：authored_summary | official_documentation_excerpt
    has_provenance: bool,                    # 该候选快照是否携带 provenance 块
    checks: PromotionChecks,                 # C1–C5/C7/C8 的逐项布尔结果（加载期填充）
    attestation: SourceVerificationAttestation | None,   # C6：外部证明；缺失即 None
) -> bool
```

**返回真的充要条件（全部成立）**：

1. `source_kind == "official_documentation_excerpt"`；且
2. `has_provenance is True`；且
3. `checks.c1/c2/c3/c4/c5/c7/c8` **全部**为真；且
4. `attestation is not None`；且
5. `attestation.overall_result == "passed"`；且
6. `attestation.verifier_version == EXPECTED_VERIFIER_VERSION`；且
7. `attestation.snapshot_set_id` 与被判定的快照集一致；且
8. **文件级自绑定（§2.2.4）**：`INDEX.json` 实际字节摘要 == `index_sha256`；
   每个 `snapshot_files[].path` 实际字节摘要 == 登记 `sha256`；
   **文件集合与 `INDEX.json` 登记的候选快照集合完全一致**（不多不少）；且
9. **声明级对齐**：每个 `source_id` 在 `documents[]` 中恰好出现一次，
   `raw_sha256` / `blob_sha` 与 provenance 登记值**逐字相等**，且该文档 `result == "passed"`。

**条件 4–9 就是 C6**；条件 1–3 是 C1–C5/C7/C8 的汇总。
**没有 attestation ⇒ 条件 4 为假 ⇒ 返回 `False`，但加载期不报错**（§2.2.2）。

**⚠️ 明确禁止的实现走法（写进实现的文档字符串）**：
**不得**只用条件 5 + 9（即"看 `overall_result` + 比 `raw_sha256`/`blob_sha`"）就判定有效。
理由：`raw_sha256` / `blob_sha` 是**写在 fixture 里的声明值**，二者一致只能证明
"两句话一致"，证明不了"被证明的快照就是磁盘上这份"。
**条件 8 的两个文件级锚点（`index_sha256` + `snapshot_files[].sha256`）必须校验。**

**可选加强模式**：若 `research_grade` 要求 `require_live_verification=True`，
则**不采信条件 5–9**，改为**当场用原件重新核对**（§2.2.3 信任模型）——
此时条件 8/9 仍需成立（用于确认"现算的对象就是这份 fixture"）。

**输入校验（不做静默兜底）**：

- `source_kind` 不在闭集内 → 抛 `SourceProvenanceSchemaError`（**不是**返回 `False`）：
  "未知来源类型"是配置错误，不是"不可升格"；
- `checks` 类型不对 → `TypeError`；
- `attestation` 非 `None` 但 schema 不符 → 抛错（不静默当作无效）。

**测试用例（`tests/research/test_promotion_gate.py`）**：

### 2.8 加载期的 `source_kind` ↔ `provenance` 交叉强制

`is_promotable_source` 是**谓词**；下面这条是**加载期闸门**（写错即报错，而不是返回 `False`）：

| `source_kind` | `provenance` 块 | 加载期行为 |
|---|---|---|
| `official_documentation_excerpt` | **必须存在**且通过 `read_provenance` 全量校验 | 缺失 → `MissingProvenanceError` |
| `authored_summary` | **必须不存在** | 出现 → `SourceProvenanceSchemaError`（人工摘要不得冒充官方来源） |
| 其它任意值 | — | `SourceProvenanceSchemaError` 并列出合法值 |

两者互为反例，任何一侧写错都在加载期报错 —— 这把"官方原文"与"人工摘要"
从"目录约定的口头区别"变成"加载期强制的机器区别"。
**注意**：这条校验读的是**文件里已存在**的 `source_kind` 与 `provenance`，
因此**不需要修改任何 fixture 字节**（§6.1.1 `G-PRESERVE`）。

#### `research_grade` 如何接入 `assemble_report`（**这是本节的核心**）

**签名变化（只增一个可选参数）**：

```
assemble_report(brief, cards, registry, *, snapshots=None, snapshot_set=None, strict=True)
```

`snapshot_set=None`（默认）⇒ **行为与今天逐字节相同** ⇒ 既有 `report_id` 全部不变。

**`snapshot_set` 携带两件事**：

| 字段 | 作用 |
|---|---|
| `snapshot_set_id` | 与 attestation 对齐；混集检测 |
| `policy` | `regression_replay`（默认语义）或 `research_grade`（强制） |
| `promotable` | `Mapping[candidate_id, bool]`：由 `is_promotable_source()`（含 attestation）预先算出 |

**强制点的落点：成为一条新的完整性检查项 `I10`**

`research_grade` 违规**不**设计成一条独立的抛错路径，而是**接入既有的 I1–I9 机制**：

| 项 | 内容 |
|---|---|
| 码 | `I10_NON_PROMOTABLE_SUPPORT` |
| 何时参与 | **仅当** `snapshot_set.policy == "research_grade"` 时进入检查序列；其它情况**不出现** |
| 判据 | 对每个候选：若存在 `finding.is_supported` 而其证据来源候选 `promotable == False` → **失败** |
| 失败信息 | 列出 `candidate_id` / `dimension_id` / `finding_id` / 原因（`absent` / `incomplete` / `version_expired` / `mismatch`） |
| **冻结失败（fail-closed）** | 声明了 `research_grade` 却**没有** `promotable` 映射（或键不全）→ 视为**失败**，不视为"无约束" |

**为什么可以安全新增 I10**：`SelectionReport.content_projection()` **显式不含 `integrity`**
（`models.py` 注释写明："完整性是评估结果，不是内容"）。
因此新增 I10 **不改变任何 `report_id`**。

**`strict` 的两种行为（对应审阅意见 4，必须写死）**：

| `strict` | 行为 |
|---|---|
| `strict=True`（默认） | `integrity.passed == False` ⇒ 抛 **`ReportIntegrityError`**（**既有**异常类型，`failed_codes` 含 `I10`）。**不返回半成品** —— 与既有 I1–I9 处理**完全一致**，不新增异常族 |
| `strict=False` | **不抛异常**，**照常返回报告**；其 `integrity.passed == False`、`failed_codes` 含 `I10`，`detail_of("I10_NON_PROMOTABLE_SUPPORT")` 给出完整违规清单 |

**`strict=False` 下"报告内容"与"降级"的边界（必须写清，避免误解）**：

1. **报告内容不变**：`supporting` / `evidence_refs` / 排名 / 评分**一律不改**。
   I10 只影响**完整性判定**，不影响内容 ⇒ `strict=True` 与 `strict=False` 的
   **`report_id` 相同**（与既有设计一致）；
2. **不允许"悄悄降级成 `regression_replay`"**：`strict=False` **不会**把违规证据从
   `supporting` 剔除，也**不会**改写 `policy`。它只**如实产出一份"未通过"的报告**；
3. **调用方有责任检查 `integrity.passed`**：这是项目既有契约
   （`03_no_trusted_evidence` 等场景就是这么用的）。P2.2-4 的评测场景将**显式断言**
   `integrity.passed == False` 且 `failed_codes` 含 `I10`，而**不是**断言"抛错"。

**为什么做成完整性码而不是直接抛错**：

- 直接抛错会让 `strict=False` 这条既有降级路径**在 `research_grade` 下失效**
  （`strict=False` 的语义就是"不要抛，给我看失败报告"）；
- 做成 I10 后，`strict` 的语义在全项目**只有一处定义**，不引入第二套开关；
- `strict=False` 因此能拿到**完整违规清单**（哪些候选、哪些维度、为什么），
  比一条异常信息更有用。

**`ResearchGradeViolation` 的定位**：**不再作为对外抛出的异常**，
只作为 I10 内部的**结构化明细类型**（承载违规清单），由 `IntegrityReport.detail_of()` 暴露。
对外契约只有两个：`ReportIntegrityError`（`strict=True`）与 `integrity.passed`（`strict=False`）。

**三条不可动摇的性质**：

1. **`research_grade` 是 opt-in**：默认不传 `snapshot_set` ⇒ 全部既有调用/测试/评测**逐字节不变**；
2. **人工摘要不可能支撑研究级推荐**：`authored_summary` 的 `promotable` 恒为 `False`（§2.7 条件 1），
   因此在 `research_grade`（`strict=True`）下**必然**抛 `ReportIntegrityError` 且 `failed_codes` 含 `I10`
   —— 这条由测试用**真实 `fixtures/research` 数据**钉死，不是合成数据；
3. **无 attestation 时官方集也不可 research_grade**：这是**有意**的
   （"没核对过原件就不算研究级"）。P2.2-4 的官方场景集在生成 attestation 之前，
   期望值是 `not_promotable`，而不是"通过"。

| 测试用例 | 期望 |

## 五、发现的现有缺陷（均已实测复现，非推测）

### D1【中】`source_kind` 被声明但**零消费** → "官方原文"与"人工摘要"实际同权

- **证据**：`source_kind` 在 `src/` 与 `tests/` 的**全部**引用只有 `sources.py` 第 5–6 行的
  **注释**；`FixtureSnapshot` / `CandidateEntry` / loader / worker / 报告链路**都不读取它**。
  6 份 fixture 文件里都写了值（3 份 `authored_summary`、3 份 `official_documentation_excerpt`）。
- **后果**：README 宣称"两个 fixture 目录分别用 `source_kind` 标注是人工摘要还是官方摘录"，
  但**代码层面两者都是 `fixture_snapshot`、同在 `TRUSTED_SOURCE_TYPES`**，
  即"人工撰写的摘要"与"官方原文摘录"在信任级上**无法区分**。
  这正是审阅要求必须区分的两类：**人工摘要只能用于 P1A 回归兼容，
  只有官方原文才可作为真实研究推荐的可信支撑**。
- **影响**：不改变现有 `report_id`（故不是回归），但**信任边界的可验证性缺失**。
- **处置**：P2.2-1 —— 让 `source_kind` 在加载期生效（§2.8）；
  新增 `is_promotable_source()` 把人工摘要**明确降级**为不可升格（§2.6.1、§2.7）。
  **不改**既有 `is_trusted_evidence` 语义（那会改 `report_id`）。

### D2【中】`locator` 校验有**两条规则不一致**的实现

- **证据（实测）**：对同一条 `EvidenceRef`（excerpt 为 section 原文的 20 字符严格前缀，
  digest 按该前缀自洽）：

  | 路径 | 实测结果 |
  |---|---|
  | `assemble._verify_fixture_locators` | **通过**（`startswith`） |
  | `OfficialSources.resolve_evidence` | **拒绝** `SourceReferenceError`（精确相等） |

- **后果**："证据可解析"不是一个良定义属性 —— 组装期认为可解析的报告，
  在来源层复核时可能解析失败。两条路径对同一输入给出相反答案。
- **影响**：现有数据**不触发**（`_evidence_for` 产出的是完整/400 截断文本，两规则都接受），
  所以 `report_id` 不变；但这是**真实的验证漏洞**：只要有人构造前缀摘录，
  组装期会放行，而来源层会拒绝 —— 两个校验器互相不知道对方的存在。
- **处置**：P2.2-2（§2.4）。

### D3【观察项，非缺陷】P2.1 采集层与证据层之间**没有自动通路**，但只有"间接"守卫

- **证据**：`OfficialSources` / `load_official_sources` 只被 `tests/` 引用，
  `eval/` 与 `src/` 的生产路径都不引用；`research` 不 import `providers`（有静态守卫）。
- **判断**：**"没有通路"是正确设计**（仓库搜索摘要不是技术结论），不是缺陷。
  但现有保护全是**间接**的（依赖方向、类型闭集），**没有一条正面机制**
  阻止"把 provider 快照内容拼成 `EvidenceRef`"。字段形状检查不够：字段是实现细节。
- **处置**：P2.2-1 升级为**受控公开 API + 静态守卫**四层边界（§2.5 L1–L4）：
  证据只能由 `PromotableExcerpt` 经唯一公开工厂产出 ⇒ 在受控 API 与 L3/L4 守卫下
  **没有合法的代码路径**能把采集结果变成证据。**注意口径**：方案**不声称**
  "类型上不可表达/物理不可能"（Python 没有构造可及性控制），只声称"不可**合法**生成"；
  并配 4 条负向/反空转测试证明该边界可证伪。

### D4【低】官方目录**零评测覆盖**

- **证据**：`eval/research/run_eval.py` 的 `FIXTURE_ROOT = PROJECT_ROOT / "fixtures" / "research"`，

### D5【低】"来源已核对"不是一个可检查的事实

### 6.6 失败与重试策略

| 层 | 策略 |
|---|---|
| **加载期**（快照/provenance） | **快速失败**：任一校验不过即抛错，**不返回部分结果**（现有 `read_provenance` 已是此语义）。**缺 attestation 不属此列**（它不参与加载，§2.2.2） |
| **组装期** | `strict=True`（默认）抛 `ReportIntegrityError` 且**不返回半成品**；`strict=False` 返回带失败码的报告（**含 `I10`**，§P2.2-3） |
| **升格判定期**（C6 自绑定） | 任一锚点不匹配 ⇒ `is_promotable_source` 返回 `False` 并记录**原因**；**不抛错**（升格失败不是加载失败） |
| **attestation 写入期** | 目标已存在且**内容不同** ⇒ **拒绝写**（W2）；发布用**原子排他**（W3：temp + fsync + `os.link`），**平台不支持时 fail-closed**（拒绝 + 退出码 1，不得降级为非原子写法）；**禁止静默把 `incomplete` 改写为 `passed`**（W4） |
| **采集期**（P2.1，不在 P2.2 范围） | 超时 / 超限 / 重定向 / 非法 URL 各有专用异常；**采集失败不得降级成"空结果"**（`{"message":...}` 错误体必须报错，不能当零结果） |
| **重试** | P2.2 **不引入重试**（确定性回放不需要）；采集层重试属 P2.3+ 且需先定义"什么错误可重试" |
| **来源复核** | 缺失（missing）与不符（problem）**分开报**；`--allow-missing` 只是显式放行缺失，**永不**放行 problem |

### 6.8 最小可交付版本（如果时间受限，做到这里即可）

按"价值 / 风险"排序，最小可用集合是 **P2.2-1 + P2.2-2**：

- 加四层受控公开 API + 静态守卫边界（D3）—— 保证"采集层不得成为证据"
  在受控 API 下**没有合法的代码路径**；

**P2.2-3 / P2.2-4 可以后置**：它们增加的是"边界清晰度"与"评测覆盖"，
不影响正确性。若必须二选一，**优先 P2.2-4（评测覆盖）**，因为 D4 意味着官方链路

### 6.9 明确仍然不实现（本阶段禁区）

**定位重申**：P2.2 = **信任边界加固 + 官方评测覆盖**。因此：

- **不实现 provider 自动升格** —— `provider.snapshot.v1` 到 `EvidenceRef` 之间
  **不存在自动通路**，且本阶段把这个"不存在"升级为**受控公开 API + 静态守卫的硬边界**
  （§2.5 L1–L4）：在受控 API 下**没有合法代码路径**能把采集结果变成证据。
  人工离线升格路径只**写出定义**（§1.2），**不写实现**。
- **不实现自主研究** —— 无查询改写、无多轮迭代、无自动结论生成；
  采集仍是一次性人工动作，组装链路零网络调用（`network_calls` 必须为 0）。
- **不把人工摘要用于研究级推荐** —— `authored_summary` 仅用于 P1A 回归兼容，
  `is_promotable_source` 对它恒为 `False`（§2.6.1、§2.7）。
- **不接 LangGraph / ACP / FastAPI / 长期 memory。**
- **不新增候选、不新增维度、不改权重。**
- **不新增第三方依赖**（`dependencies = []` 保持）。
- **不改 `scripts/` / `assets/` / `materials/`；不改 `fixtures/**` 字节、不重签**（§6.1.1）。
- **不改 P1A 的 `report_id` / 历史 expectations / 既有 eval 结果。**
- **不新增 `EvidenceRef` 字段、不扩 `ALLOWED_SOURCE_TYPES`、不改 `is_trusted_evidence` 语义。**
- **不实现数字签名**：attestation 的信任模型是"过程保证"（§2.2.3），**不声称**密码学保证；
  需要更强保证时用 `live_reverify` 模式（当场用原件重算），但该模式**仍不联网**。
- **不新增 attestation 的自动重写路径**：写入遵守 W1–W4；
  `incomplete` → `passed` 只能通过"显式删除旧文件 + 重新核对"完成，**不存在静默改写**。
- **不改 `tools/` 既有行为**：只增 `--write-attestation` 等 opt-in 参数，
  既有 `--raw-dir` / `--allow-missing` / `--json` 与退出码语义不变。
