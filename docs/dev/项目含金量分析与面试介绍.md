# 主 Agent 调度与多 Agent 协作 · 含金量分析与面试介绍

> 本文基于项目实际代码（`主Agent调度与多Agent协作.md` + `scripts/01~05` + `materials/product_goal.txt`）逐行核实整理。
> 定位：这是一个**多 Agent 协作的工程范式演示项目**——用一个「主 Agent 当调度中心 + 多个子 Agent 当执行单元」的方式，解决「单个 AI 干长任务会越聊越乱」的真实工程问题。

---

## 一、项目一句话定位

把一个大目标（如「做一份杭州三日游团建方案」）交给一个**主 Agent（项目经理）**，它由模型**动态拆成任务看板**，再把每张任务卡裁剪成**只含必要信息的私有任务包**发给子 Agent，**回收结果、管依赖、管失败重试**，最后综合成一份可交付的报告。核心是**上下文隔离 + 可观察的调度**，而不是简单地把几个模型拼在一起。

---

## 二、核心价值：它到底解决了什么真问题

单 Agent 跑长任务，最典型的失败不是「完全不会做」，而是**中途开始混乱**：一段对话里混着用户目标、工具日志、失败尝试、半成品结论、模型自我解释。后续步骤分不清哪些是真的、哪些只是临时推理。这就是行业里说的**上下文污染（context pollution）**。

本项目针对这个痛点，把问题变成清晰的工程责任：

| 单 Agent 的乱象 | 本项目的解法 |
|---|---|
| 所有中间过程混进同一条对话 | 子 Agent 只回公开摘要，**私有过程不回流** |
| 做到哪步靠模型「感觉」 | 主 Agent 把进度写进**任务看板（board）** |
| 子任务说完成，但没证据 | 回收 `session_id`、结果文本、状态变化 |
| 一个子问题挂了，主会话继续堆垃圾 | 失败**留在具体任务卡上**，主 Agent 决定重试或人工确认 |

**所以含金量不在「用了几个 Agent」，而在「把多 Agent 的边界、状态、权限、证据归属讲清楚并跑通了」**——这正是区分「真做过 Agent 工程」和「只是调了个 API」的关键。

## 三、技术亮点清单（这部分是真正能讲的价值）

1. **上下文隔离（Context Isolation）—— 全场最核心的设计**
   每张任务卡拆成三类数据：`TaskCard`（公共状态）/ `WorkerTaskInput`（私有任务包）/ `WorkerResult`（回收结果）。下游子 Agent 只能看到「显式依赖的上游公开摘要」，看不到完整主会话，也看不到其它卡片的私有过程。代码里 `build_worker_input()` 会校验依赖是否完成，没完成就禁止它自己瞎猜。

2. **动态任务板 + 结构护栏（不盲信模型）**
   任务几张卡、归谁、谁依赖谁，全由主 Agent 的模型**真实决定**（不写死三段流程）。但进执行前过一层**护栏校验**：任务数量 2–6 张、子 Agent 只限白名单 `{codex_research, codex_plan}`、`task_id` 正则 `^[a-z][a-z0-9_]{1,40}$`、依赖必须存在、且**至少一条协作依赖边**。`validate_model_board()` 明确写明「模型给不出可执行看板就直接报错暴露，不偷偷换成预设答案」。

3. **DAG 依赖环检测**
   `ensure_board_is_dag()` 用逐层消解算法检测循环依赖——只要某一轮找不到可解任务，就判依赖成环。保证调度顺序永远可推进。

4. **ACP 协议接入（协议层边界清晰）**
   用 **Agent Client Protocol（ACP）** 把本地 Codex 接成标准会话：`initialize → new_session → prompt → session/update`。主 Agent 完全不关心 Codex 怎么启动、怎么流式输出、怎么申请权限——这些都被协议收口。文档还专门厘清了 **ACP（服务内主从调度）vs A2A（跨服务/跨团队 Agent 发现协作）的协议边界**，并说明本文为什么不用 A2A。

5. **TriggerFlow 托管主 Agent Loop（流程可观察、可复盘）**
   把「建板 → 派活 → 回收 → 综合」拆成 3 个阶段 chunk：`plan_board` / `dispatch_tasks` / `synthesize_report`，用 `to()` / `when()` 装配。全局状态存在 `state["board"]`，执行过程持续吐出 `board_created / task_started / worker_delta / task_done / dispatch_done / final_report_ready` 业务事件。

6. **流式进度（worker_delta）**
   子 Agent 每吐一段文字，就转成 `worker_delta` 事件推给外部观察者，长任务也能实时看到「哪张卡在推进、子 Agent 说了啥」，而不是干等一个最终输出。

7. **失败 / 重试边界**
   `MAX_ATTEMPTS = 2`，失败任务留在卡片上，主 Agent 决定重试还是标记 `failed` 并阻塞，不会让一个子问题污染整次运行。

8. **真实可运行，不是 PPT**
   主 Agent 用 DeepSeek（`temperature=0` 保证稳定），两个子 Agent 是本地 Codex ACP worker；5 个独立脚本（`01_plan_board` → `05` 复盘）从读目标、建板、连 worker、跑 Loop 到校验结果，逐个能单独跑通，并落 JSON 运行产物供对照。

## 四、具体做了什么：功能与模块

**三类数据契约（设计基座）**
- `TaskCard`：公共看板上的一张状态卡（id / 标题 / 负责 agent / 目标 / 可见背景 / 依赖 / 状态 / 结果 / session_id / 重试次数）。
- `WorkerTaskInput`：发给单个子 Agent 的私有任务包（含 `goal / context / upstream_results / acceptance / forbidden`）。
- `WorkerResult`：主 Agent 回收的公开结果（含 `session_id / stop_reason / permission_decisions`），私有过程不入板。

**调度判断**
- `decide_board_action()`：只读公共看板，输出 `dispatch / retry / blocked / finish` 四种动作，是「继续 / 重试 / 阻塞 / 结束」的唯一依据。

**ACP 连接层**
- `AcpWorkerClient`：收文本、记事件类型、子 Agent 申请读写/执行命令时**默认拒绝**（课程只验证调度与回收）。
- `AcpWorkerSession`：完整会话生命周期，同一 `session_id` 可多轮 prompt。

**编排层（TriggerFlow）**
- `plan_board`：主 Agent 建板，写入全局 state。
- `dispatch_tasks`：循环读板 → 选 ready 卡 → 裁剪私有包 → 调 worker → 回写结果 / 重试。
- `synthesize_report`：读完整看板，主 Agent 综合成面向组织者的报告（综合摘要 / 已确认事实 / 信息缺口 / 方案草案 / 风险 / 下一步问题）。

**演示业务场景**
- `materials/product_goal.txt`：杭州三天两晚团建规划，要求兼顾景点节奏、交通、活动、预算、天气备选、安全边界，输出面向组织者。

**产物**
- `9` 张 SVG 架构/流程图（主从架构、业务流程、ACP 连接、任务板生成链路、私有任务包裁剪等）。
- `5` 个可独立运行的 Python 脚本 + `.demo_runs/` 下的 JSON 运行记录。

## 五、开发流程与时间线（逻辑顺序）

> 说明：这是从代码结构 + 文档「理论→ACP→实战」三层递进反推的**自然构建顺序**（项目本身为课程演示，无独立日历排期）。面试时按这个顺序讲，评委能清楚看到你的工程思考递进。

| 阶段 | 做了什么 | 对应产出 |
|---|---|---|
| **Phase 1 · 问题建模** | 先讲清单 Agent 长任务的 4 类乱象，定下「主 Agent 管全局状态、子 Agent 只拿私有包」的责任边界 | 理论篇 + 主从架构图 |
| **Phase 2 · 数据契约设计** | 定义 `TaskCard / WorkerTaskInput / WorkerResult / BoardDecision` 三类半数据，把「共享什么、隔离什么」钉死 | `scripts` 里的 dataclass |
| **Phase 3 · 协议接入** | 引入 ACP，跑通 `initialize→new_session→prompt` 最小连接，并厘清 ACP vs A2A 边界 | `02_worker_acp_smoke.py` + ACP 图 |
| **Phase 4 · 动态建板 + 护栏** | 主 Agent 真实拆任务，写护栏（数量/白名单/正则/DAG 环检测/至少一条协作边） | `01_plan_board.py` + 建板链路图 |
| **Phase 5 · 上下文隔离验证** | 把看板裁成私有包发给子 Agent，验证下游只拿到显式上游结果 | `03_context_isolation.py` + 私有包裁剪图 |
| **Phase 6 · 主 Loop 编排 + 可观察** | 用 TriggerFlow 串起三阶段，加流式 `worker_delta`、失败重试、最终综合报告 | `04_triggerflow_master_loop.py` |
| **Phase 7 · 复盘** | 读运行产物，校验看板全 `done`、有 `worker_delta` 流式输出，打印最终报告 | `05_hangzhou_team_building_run.py` |

## 六、面向面试官的项目介绍（大白话版，可直接读/改）

> 下面这段刻意用「技术小白也能听懂」的口语，面试时照这个节奏讲，再展开技术细节。

**开场（30 秒版）：**
「我做了一个多 Agent 协作的调度小系统。你可以把它理解成一个**项目经理带两个专家干活**。

平时我们让一个 AI 一口气干完一个大任务，干到后面它自己就乱了——前面聊过什么、试错过什么、半截的结论全混在一起，AI 分不清哪些是真的、哪些是瞎猜的，这叫『上下文污染』。

我的系统换了个思路：用一个『主 Agent』当项目经理，它**不亲自干活**，而是先把老板给的大目标（比如『做一份杭州三日游团建方案』）拆成几张任务卡贴在看板上，每张卡交给一个子 Agent（一个偏调研、一个偏方案）。**关键是我做了一层信息隔离**——每个子 Agent 只能看到自己那张卡需要的内容，看不到别的卡、也看不到完整对话，所以它不会被无关信息带偏。干完一张，主 Agent 把结果收回来贴回看板，再决定下一张谁来做、谁依赖谁（用有向无环图管先后），最后把所有结果**综合成一份给老板看的报告**。」

**展开（技术亮点，挑 2–3 个讲）：**
- 「子 Agent 之间不会互相串味，靠的是我把信息拆成『公共看板 / 私有任务包 / 回收结果』三类，下游只能拿到上游明确交出来的那部分。」
- 「任务怎么拆、谁依赖谁，是模型自己决定的，但我加了结构护栏——任务数量、依赖不能成环、子 Agent 只能调白名单里的，防止模型乱生成。」
- 「整个流程用 TriggerFlow 串起来，每一步（建板、派活、完成、综合）都有事件可观察、可回放，失败时卡在具体的任务上，不会污染整次运行。」

**个人贡献表述（按真实情况选，别硬夸）：**
- 设计了「公共看板 + 私有任务包 + 回收结果」的三类数据隔离方案，从根上压制上下文污染；
- 实现了动态任务板生成与结构护栏（数量/白名单/DAG 环检测/协作依赖校验），让模型输出可进生产；
- 用 ACP 协议接入本地 Codex 作为子 Agent，厘清了 ACP 与 A2A 的协议边界；
- 用 TriggerFlow 把「建板→派活→回收→综合」编排为可观察、可重试、可复盘的主循环；
- 产出 9 张架构图 + 5 个可独立运行的脚本，覆盖从连接验证到完整复盘的全链路。

## 七、面试防御：别踩的坑（诚实边界）

这部分是帮你**别被追问翻车**的，建议心里有数：

- **它是范式演示，不是线上产品**：围绕单场景（杭州团建）跑通，没有用户系统 / 数据库 / 部署。卖点是**架构思维与工程纪律**，不是「上线了多少用户」。
- **子 Agent 被刻意限制**：`forbidden` 里写明「不读文件、不跑命令、不联网」，只返回文字结论——这是**教学设计**，不是能力缺失。被问到就说「为了把『调度与上下文隔离』这条主线讲清楚，故意把工具调用摘掉了，真实系统里子 Agent 可以挂工具」。
- **主 Agent 用 DeepSeek，子 Agent 用本地 Codex**：是**异构多 Agent**（调度层和执行层不同模型），这点反而能讲——说明你理解「主从可以用不同运行时」。
- **ACP worker 依赖本机装了 Codex + 登录 + 额度**：所以 demo 能否跑通受环境约束，提前说明即可。
- **别说「自动规划一切」**：本项目的护栏恰恰说明「模型输出必须被校验才能进执行」，这是工程严谨，不是模型自由发挥。

**一句话收尾（如果被问『这项目最大的收获』）：**
「我真正搞懂了——多 Agent 不是把模型连起来就完事，难的是**状态归谁、信息谁能看、失败谁兜**。把这几条边界钉死，系统才可控、可复盘。」
