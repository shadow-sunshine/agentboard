## 0. 现状诊断：为什么 attempt 2 仍被重放绕过

当前代码里"证明"与"本次数据"之间缺三段即时核对，B6 的重放正是从这三段缺口通过的：

| # | 缺口 | 现状（attempt 2 代码） |
|---|---|---|
| G-1 | **内存快照 ↔ 磁盘字节无对应性** | `FixtureSnapshot` 不携带来源文件摘要；`load_snapshot` 在加载期做过 C7（sha256 == INDEX 登记），但该事实不随对象存续。组装期拿到的内存快照与任何磁盘文件都没有机器可查的对应关系 |
| G-2 | **绑定是过去时刻的事实，组装期不重验** | `_attestation_blocking_reason`（integrity.py:300-323）只检查 attestation 对象自身的属性（binding_reason / verifier_version / snapshot_set_id / overall_result）——全部是 `load_attestation()` **当时**的结论。"绑定时刻的磁盘"与"组装时刻的数据"之间无任何现读现算 |
| G-3 | **证据摘录的核对基准是内存** | `_verify_fixture_locators`（assemble.py）用内存快照做基准：内存文本被改，摘录与 locator 照样自洽（B6 负控正是这样通过的） |

因此 attempt 2 的 I10 实际上只证明了"曾经有一份有效证明存在"，没有证明"这份证明核对的字节 == 本次组装消费的字节"。

## 1. 绑定链精确定义（逐跳：权威 / 校验位置 / 失效行为）

设计总原则：**磁盘字节是唯一权威，内存对象一律不可信；任何"事实"必须在使用它的时刻当场重测，不得引用历史测量结论作为充分条件。**

```
candidate_id --H1--> fixture 文件路径 --H2--> 磁盘文件字节 --H3--> attestation
                                        |--H4--> 内存 FixtureSnapshot --H5--> finding/evidence
 SnapshotSet + attestation --H6--> 本次组装（同源性）
```

### H1 candidate_id → fixture 文件路径

- **权威**：`INDEX.json.candidates[].fixture_path`（磁盘上的索引文件）。
- **校验位置**：
  - 加载期（现有）：`load_snapshots` 按 `catalog.candidates` 逐个加载；
  - **组装期（新增）**：`FixtureSnapshot` 携带加载期戳印 `fixture_relpath`；research_grade 组装要求每个参与快照的 `fixture_relpath` 非空，且 (candidate_id → fixture_relpath) 组合在 attestation 的 `snapshot_files[]` 中**存在且唯一**。
- **失效行为**：戳印缺失（`""`）或不在 attestation 覆盖集内 ⇒ I10 明细 `uncovered_candidate`（fail-closed）。

### H2 文件路径 → 磁盘文件字节（单次读取契约）

- **权威**：**磁盘字节本身**。任何 sha256（INDEX 登记的、加载期算的、attestation 登记的）都是关于字节的**声明**，只有当场现算的哈希是测量。
- **单次读取契约（rev 2，堵组装内 TOCTOU）**：每个文件在**单次组装内恰好从磁盘读取一次**，读入的 raw bytes 存入**不可变字节缓冲**；该文件的摘要计算与 JSON 解析**必须基于同一份缓冲**——
  - 摘要 = `sha256(缓冲)`（与 attestation 登记值比对）；
  - 内容 = `json.loads(缓冲)`（与内存快照比对，见 H4）。
  禁止"先读一次算摘要、再重读一次解析"的两开模式：两次打开之间文件被替换时，哈希验的是旧字节、解析的是新字节，防线静默失效。
- **校验位置**：
  - 加载期（现有，C7）：`_verify_file_digest` 对比 INDEX 登记值（加载期行为不变，不属于本跳）；
  - **组装期（新增，核心）**：S0.5 对每个参与组装的快照文件按单次读取契约测量，现算摘要与 attestation 的 `snapshot_files[].sha256` 精确比对。
- **失效行为**：现算值 ≠ attestation 登记值 ⇒ I10 明细 `disk_mismatch:<path>`；文件读不到 ⇒ 同判（fail-closed，不区分"文件没了"和"文件被换了"）。

### H3 磁盘字节 → attestation（文件层）

- **权威**：attestation 的 `index_sha256` + `snapshot_files[].sha256`（由核对工具在生成时写入，**与当前磁盘无关的登记基准**）。
- **校验位置**：
  - 绑定时刻（现有）：`load_attestation()` → `_binding_reason()` 做三层锚点（L-a/L-b/L-c）；
  - **组装时刻（新增，核心）**：对 `fixture_root` **重新执行同一测量**（复用同一实现，**不写第二份**——R6；且按 H2 单次读取契约，测量与解析共用同一份字节缓冲）。绑定时刻的通过结论不进入本次判定，只作为日志/明细参考。
- **失效行为**：重测得到任何非 `""` 原因 ⇒ I10 明细按原因细分（`mismatch`：文件集合多/少/摘要不等/INDEX 变更）。
- **为何这一跳能堵"换目录/旧证明重放"**：attestation 登记的是**字节摘要**而非"某目录身份"。重放到字节不同的目录，现算摘要必然对不上——无论 `snapshot_set_id` 字符串是否相同。

### H3b attestation 声明层完整性（documents[] ↔ 当前 provenance 并集）

> rev 2 新增。**独立负控已复现的缺口**：真实官方 fixture + 有效 passed 证明，把证明的
> `documents` 清空后 `load_attestation` 仍给出 `binding_reason=""` —— 文件层锚点
> （L-a/L-b）只验字节，不验"证明是否覆盖了全部已声明文档"。

- **权威**：参与组装快照的 **provenance 声明并集**（`source_id → (raw_sha256, blob_sha)`，由 `sources.snapshot_set_document_digests()` 从 H4 已核验的快照内容计算——即"当前 provenance 声明什么"，不是证明自己声称什么）。
- **校验位置**（组装期 S0.5，两查缺一不可）：
  1. **精确等集**：`attestation.documents[]` 的 `source_id` 集合 == 声明并集的集合（"少"= 有文档没被证明，"多"= 证明覆盖了不属于本快照集的文档）；
  2. **逐项核对**：每个 `source_id` 的 `raw_sha256` / `blob_sha` == 声明值，且 `result == passed`。
- **唯一实现点（R6）**：上述核对逻辑从 `attestation.promotion_blocking_reason` 的文档段**抽成共享纯函数**（如 `documents_blocking_reason(attestation, declared_documents) -> str`），`promotion_blocking_reason` 与组装期 S0.5 **共用同一实现**——`documents=[]` 在任何入口都不可能得到"证明有效"。
- **加载期加固（同轮设计）**：`SourceVerificationAttestation.from_dict` 增加schema 级约束——`documents` 为空列表即 `AttestationSchemaError`（空证明在解析层就不合法）。两层防线：空集在解析层死，非空但缺/多/不符在组装层死。
- **失效行为**：等集不等 ⇒ `mismatch`；某项 `result != passed` ⇒ `incomplete`；`raw_sha256`/`blob_sha` 不符 ⇒ `mismatch`。与既有五原因同闭集、可区分。

### H4 磁盘字节 → 内存 FixtureSnapshot（堵 B6 的关键一跳）

- **权威**：H2 单次读取契约下**同一份字节缓冲**解析出的内容（`json.loads(缓冲)` + 既有解析规则）——不是第二次读盘的结果。
- **校验位置**：**组装期内容级现读现比（新增）**——内存快照与同缓冲解析结果逐项比较：`snapshot_version` / `captured_at` / `source_kind` / 每个 section 的 `section_id`+`heading`+`text` / 每个 `dimension_value`。比较用唯一截断实现所在层的既有解析路径（R6）。
- **失效行为**：任一项不等 ⇒ I10 明细 `tampered_in_memory:<candidate_id>/<section_id>`（B6 负控改的 section 文本在这一跳被抓）。
- **诚实说明**：内存对象与磁盘字节**逐字段相等**是这一跳能给出的最强对应——不引入对内存对象的哈希信任（那是循环论证：内存哈希本身可被篡改）。

### H5 内存 snapshot → finding / evidence（含证据单独被篡改的语义，rev 2 钉死）

- **权威**：locator 形态（`/sections/<index>/text` 唯一正则）+ 规范截断（`expected_excerpt_for` 全仓唯一实现）+ H4 已核验的磁盘内容。
- **校验位置**：
  - 现有（S2）：`_verify_fixture_locators` —— 摘录必须恰好等于 locator 指向原文的规范截断；
  - **重设计（P2.2-3 范围内）**：research_grade 下该检查的**基准切换为 H4 已核验的磁盘内容**（经 H4 后内存 == 磁盘，正控无行为差异，但消除"内存自洽"盲区）。
- **证据单独被篡改的语义（rev 2 明确，不留选择空间）**：
  - **场景**：snapshot 与 attestation 均不变，仅 card 产出的 `EvidenceRef` 的 `locator` / `excerpt` 被改（locator 悬空、或 excerpt ≠ 已核验字节的规范截断）。
  - **判定**：research_grade 下一律记为 **I10 失败**，原因 `evidence_mismatch:<candidate_id>/<locator>`（悬空 locator 与截断不等**同码不同 detail**，均在明细中可定位）；**不是**抛既有的输入校验异常、也不新增检查码。
  - **理由**：证据被单独篡改与快照被篡改是同一性质的问题——"报告内容没有对应到被证明的字节"，属于 R1 完整性判定的管辖范围；若走异常路径，`strict=False` 的"返回 I10 未通过报告"契约就会被绕过（异常不带完整性判定）。既有 `DanglingSectionError` 等**默认路径行为不变**（P1A 字节稳定），仅 research_grade 组装在 S0.5 内改记 I10。
- **失效行为**：`strict=True` ⇒ `ReportIntegrityError`（failed_codes 含 I10）；`strict=False` ⇒ 返回 `passed=False` 的 I10 报告，内容不清洗。

### H6 attestation → 本次组装（同源性）

- **权威**：`load_snapshot_set()`（新 loader-only 工厂，见 §3-D2）建立的 **root ↔ attestation 绑定上下文**：H2/H3/H4 组装期现算时，只允许使用工厂携带的 `fixture_root`——它与 attestation 绑定时的 root 同源。
- **校验位置**：工厂内做一次绑定（复用 `load_attestation`）；组装期所有现算都取该 root。
- **失效行为**：research_grade 的 `SnapshotSet` 无 `binding_context`（或非工厂产物）⇒ I10 `unbound`（与"attestation 未绑定"同因：来源不可证明）。
- **为何这一跳必要**：若 `fixture_root` 由调用方随 `assemble_report` 传参，就会出现"attestation 绑定目录 A、现算却对目录 B 执行"的新伪造面；同源性必须在 loader 侧一次性建立。

### 显式声明：以下均**不构成**证明

相同 `snapshot_set_id`（标签）· 相同 `source_kind`（类型声明）· "曾经 `load_attestation` 成功"（过去时刻事实）· `SnapshotSet` 上的任何声明字段 · loader 戳印字段本身（`fixture_relpath`/`fixture_sha256` 只是"组装期该去哪现读"的索引，公开构造器可填任意值；它们失效的后果只是把对应快照判为 `uncovered_candidate`，不可能**制造**通过）。

## 2. 攻击矩阵（6 负控 + 1 正控；每项含两态断言与内容契约）

统一约定：全部在**真实 `fixtures/official`**（或其 tmp 逐字节克隆）上执行；每项除下列断言外，一律加"**内容契约断言**"：失败报告（`strict=False`）的 `findings` / `supporting` / `evidence_refs` / 排名 / 评分 / policy 与正控报告**逐字节一致**（未静默过滤/清洗）；`strict=True` 与 `strict=False` 对同一内容 `report_id` 相同。

|---|---|---|---|---|---|
| **P0** | **正控** | 真实官方目录 + `verify_sources --write-attestation`（落 tmp）+ `load_snapshot_set` → 组装 | —— 通过 | `integrity.passed=True`；`report_id=rp_9e0057b9f989020f` 复现 | 同左 |
| **A1** | **内存改 section 文本**（B6 原路径） | `load_snapshot_set` 后用 `dataclasses.replace`-等价手法（经公开 API：构造含被改文本的合成快照 + 混入）替换某候选 section 文本 | `tampered_in_memory:<cid>/<sid>` | 抛 `ReportIntegrityError`（failed_codes 含 I10），不返回半成品 | `passed=False`、`failed_codes` 含 I10、`detail_of` 含 tampered 项与 candidate/section 定位 |
| **A2** | **旧证明重放 / 换目录**（含同 set_id） | attestation 绑定官方目录后，对**字节不同的另一目录**（改一个 tmp 克隆文件）用相同 `snapshot_set_id` 组装；另做"attestation 来自目录 X、组装数据来自目录 Y"的工厂外拼装（应拿不到合法 binding_context） | `mismatch`（现算 INDEX/文件摘要 ≠ 登记） | 抛 `ReportIntegrityError` | `passed=False`、原因 `mismatch`、明细含差异路径 |

| **A5** | **未绑定证明** | `SourceVerificationAttestation.from_dict(...)`（跳过 loader）直接入组装 | `unbound`（binding is None，fail-closed） | 抛 `ReportIntegrityError` | `passed=False`、原因 `unbound` |

反空转自查（R7）：A1 把 H4 现读现比回退为"信任内存"即变红；A2/A2b 把组装期重验回退为"信任 binding_reason"即变红；A3 把覆盖集检查删掉即变红；**A4① 把 schema 空文档约束删掉、或 A4②③ 把 H3b 等集检查从 S0.5 删掉即变红（回归测试同时钉住 loader 行为：documents=[] 的解析必须失败）**；A5 把 unbound 判定放宽即变红；**A6 把 `evidence_mismatch` 从 I10 改回异常路径即变红（断言 strict=False 必须返回报告）**——每条负控各钉一个机制的生效点。

## 3. 数据流与 API 变更（均为设计，未实现）

### D1 `FixtureSnapshot` 加载期戳印（`snapshot.py`）

- 新增字段：`fixture_relpath: str = ""`、`fixture_sha256: str = ""`（带默认值 ⇒ P1A 既有构造与序列化零影响；`to_dict` 是否导出见开放问题 4）。
- `load_snapshot` 在 `_verify_file_digest` 通过后填充（loader 传入 `relpath` 与已算哈希）。
- 定位：**索引，非权威**（见 §1 末段），不引入新伪造面。

### D2 `SnapshotSet` 绑定上下文 + loader-only 工厂（`snapshot.py` + L5 守卫）

- 新增内部类型 `SnapshotSetBinding`：携带 `fixture_root`（规范化的绝对路径字符串）与绑定时刻测量值（`index_sha256`、`snapshot_files` 摘要——**仅作明细展示，非判定依据**）。
- `SnapshotSet` 新增字段 `binding_context: SnapshotSetBinding | None = None`（模式与 `attestation.binding` 相同的"受控公开 API + 静态守卫"口径：公开构造器**可以**传参，但 `SnapshotSetBinding` 的构造点被 L5 静态守卫限制在 `snapshot.py`，蓄意绕过属修改行为，由守卫与评审捕获——B3 教训的准确能力边界表述）。
- 新工厂 `load_snapshot_set(*, fixture_root: Path, attestation_path: Path, policy: str) -> SnapshotSet`：内部调用 `load_attestation`（绑定不通过即抛错，不产出半成品）+ 构造 `SnapshotSetBinding` ⇒ root 与 attestation **同源一次性建立**（H6）。
- `policy=research_grade` 时 `binding_context is None` ⇒ I10 `unbound`（fail-closed）；`regression_replay` 不要求（默认路径零改动）。

### D3 组装期重验唯一实现（`attestation.py`，rev 2 拆两层）

- **文件层**：现 `_binding_reason` 重构为"纯核心 + 磁盘包装"——
  纯核心 `binding_reason_from_bytes(attestation, index_bytes, snapshot_file_bytes: Mapping[str, bytes]) -> (reason, detail)`（只吃字节缓冲，可测）；
  磁盘包装 `verify_attestation_against(attestation, fixture_root)` 按 H2 单次读取契约读盘后调用纯核心。
  `load_attestation` 与组装期 S0.5 **共用同一纯核心**（R6）；`fixture_fingerprint` 改为基于同一缓冲实现。
- **声明层（H3b）**：从 `promotion_blocking_reason` 抽出文档核对段为共享纯函数

  `promotion_blocking_reason` 与 S0.5 共用；声明并集由 `sources.snapshot_set_document_digests()` 从 H4 已核验内容计算。
- **解析层加固**：`from_dict` 拒绝空 `documents`（schema 级）。
- 不新增"绑定缓存"：每次组装现读现算（官方集 4 个小文件，成本可忽略）。

### D5 组装流程（`assemble.py`）

- S0 预检后新增 S0.5（仅 `snapshot_set.policy == research_grade` 时执行）：
  1. 校验每个参与快照的戳印与 attestation 覆盖集（H1）；
  2. **单次读取**：对参与候选的全部快照文件 + `INDEX.json` 各 `read_bytes()` 一次，存不可变缓冲；
  3. 文件层：以同一缓冲调纯核心 `binding_reason_from_bytes`（H2/H3，含 `INDEX.json` 摘要核对）；
  4. 声明层：`documents_blocking_reason`（H3b，声明并集来自同缓冲解析内容）；
  5. 内容级：同缓冲解析结果与内存快照逐项比较（H4）；
  6. 证据级：每条 fixture 证据的 locator/excerpt 对已核验内容重算，`evidence_mismatch` 记入 I10（H5）。

## 5. 信任模型与保证边界（诚实声明）

- **不做数字签名**。attestation 与 fixture 同仓存放：能改仓库的人能同时改两者并同步重签，这种攻击**无法被工具单方识破**——由 git 历史 + 代码评审 + `G-PRESERVE` 门禁（fixtures 冻结 + manifest 校验）提供过程保证。
- 本设计**保证**的命题："组装时刻消费的内存数据，逐字节对应于 attestation 生成时刻核对过的磁盘字节"——即堵住**重放**（旧证明 × 新数据）、**内存篡改**（B6）、**绑定后磁盘漂移**（TOCTOU）与**覆盖缺口**四类攻击。
- 本设计**不声称**抵御：有权改写仓库内容并同步重签的攻击者；改写运行时代码/测试的攻击者；`SnapshotSetBinding` 的蓄意构造绕过（属修改行为，由 L5 静态守卫与评审捕获，B3 的能力边界口径）。
- 结论措辞沿用 attestation.py 的既有标准："证明的是有人在某个时点按登记规则核对过这批字节"，不是"这批字节绝对可信"。
